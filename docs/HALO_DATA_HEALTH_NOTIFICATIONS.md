# HALO Data Health notifications

HALO owns the alert decision and delivery. EventBridge invokes the existing Noise Lambda at `POST /api/halo-data-health` every five minutes; that route only POSTs `{}` to HALO's `POST /api/data-health/notify`. The relay never reads Noise health or sends WhatsApp messages.

Apply `supabase/halo_data_health_notifications.sql` in the shared Supabase project before enabling the scheduler. The `ops` schema must be exposed to PostgREST. HALO needs these server-only Amplify variables: `HALO_DATA_HEALTH_TOKEN` (at least 32 random characters), `HALO_DATA_HEALTH_SEND_URL` (the listener `/send-message` HTTPS URL), `HALO_DATA_HEALTH_GROUP_ID` (one internal team group), `HALO_DATA_HEALTH_CLIENT_ID`, `HALO_DATA_HEALTH_INSTANCE_NAME`, and `HALO_DATA_HEALTH_LISTENER_TOKEN` (the listener proxy token, without `Bearer `). Noise Lambda needs `HALO_DATA_HEALTH_URL=https://<halo-host>/api/data-health/notify` and the same `HALO_DATA_HEALTH_TOKEN`.

The route sends one estate summary for each eight-hour window ending at 00:00, 08:00, and 16:00 SGT. The five-minute relay remains in place; only calls in the first fifteen minutes after a boundary are eligible. Process errors are read from the preceding window, including errors that later recovered. Current red and amber readings, standing faults, and whole-service findings are also included and labelled as current. Stale (dark-green) readings and recovery events are not red/orange issues.

The message has a header for every HALO service. Each red or orange line names its project code, process/status, and error. Identical findings across runs or projects are combined on one line, with a repeat count. A service with no reported issues has a ✅ line; when none of the services has an issue, the message also starts with ✅. The sender requires all service configuration reads and the full bounded process-history read before claiming a window, so a failed read cannot silently produce a healthy report.

`ops.data_health_notifications` is a durable unique-key claim before delivery. One key per window allows one message at most, even if the relay invokes HALO several times in the fifteen-minute eligibility period. Later ticks check that key before making the expensive health reads. Outside the eligibility period HALO returns before any database read. An ambiguous listener result remains `unconfirmed` and is not retried blindly, because the listener may already have queued it. Inspect the ledger and listener queue when a relay run fails. Removing the EventBridge rule immediately stops new evaluations. Existing service-owned Noise and WBGT Data Health crons remain separate until the HALO path has been verified live and deliberately cut over.
